# CH6 GUIDED telemetry repair — 2026-09-29

During the 21:28–21:29 flight, CH6 reached the Pi (1000/2000 PWM), but the action executor rejected FOLLOW with `REJECTED_STALE_FLIGHT_TELEMETRY`. The Pi had no `/mavros/local_position/pose` or velocity then. The FC's TELEM1 stream parameters were `MAV2_POSITION=0`, `MAV2_EXT_STAT=0`, and `MAV2_EXTRA1/2/3=0`; `MAV2_RC_CHAN=5` explains why CH6 was visible while flight telemetry was missing.

The FC was disarmed and showed the hardware safety switch before writes. The TELEM1 MAVLink stream rates were set and read back as `MAV2_EXT_STAT=2`, `MAV2_RC_CHAN=5`, `MAV2_POSITION=10`, `MAV2_EXTRA1=10`, `MAV2_EXTRA2=3`, and `MAV2_EXTRA3=3` Hz. The 10 Hz position target is needed because the action executor rejects pose or velocity older than 0.3 s; the former 3 Hz setting had a 333 ms nominal interval.

A short raw UART sample at 57600 baud confirmed that optical-flow and distance-sensor traffic nearly filled the serial link while flight-controller position messages remained sparse. ArduPilot routes MAVLink between telemetry ports; disabling routing would also hide the range sensor from the Pi. TELEM1 `SERIAL1_BAUD` and Pi MAVROS `fcu_url` were therefore both changed from 57600 to 115200, and the FC and MAVROS were restarted. `SERIAL1_PROTOCOL=2` (MAVLink2) was unchanged. The raw capture is retained only in the local maintenance evidence and is not published in this repository.

After the restart, the FC reported `SERIAL1_BAUD=115`; MAVROS and the control API reported connected, disarmed, STABILIZE, and on ground. ROS measured `/mavros/local_position/pose` at 9.996 Hz (223 samples, 52–148 ms interval) and `/mavros/local_position/velocity_local` at 9.998 Hz (107 samples, 33–162 ms interval). The hardware action executor uses `state_maximum_age_s=2.0`, while the pose and velocity limits remain 0.3 s. No arm, GUIDED mode, or motor command was issued during this validation.

In a subsequent prop-less bench session, the pilot armed in LOITER and RC CH6 reached 2000 PWM. The Pi reported an authorized pilot session, fresh FOLLOW requests and a healthy Tag 0 candidate at times. FOLLOW was rejected with `REJECTED_EKF_UNHEALTHY`, and the FC remained in LOITER. Holding CH6 high also exposed failed automatic requests being recreated near the executor loop rate; the deployed executor now spaces automatic FOLLOW retries by at least one second.

Further inspection showed that `/mavros/estimator_status` publishes no messages for this ArduPilot FC: MAVROS expects the common `ESTIMATOR_STATUS` message, while ArduPilot emits `EKF_STATUS_REPORT` (MAVLink message 193). The Pi receives that report on `/uas1/mavlink_source`. A flight-controller report with flags `367` included valid attitude, horizontal velocity and horizontal relative position. The earlier GPS `-1` observation alone therefore did not establish an unhealthy EKF, because optical-flow relative position can be valid without GPS.

The executor now decodes flight-controller-origin `EKF_STATUS_REPORT`, requires valid attitude, horizontal velocity and relative or absolute horizontal position, and fails closed for constant-position, uninitialized and GPS-glitch flags. The update retains both freshness and EKF safety gates. It was deployed while the vehicle was connected, disarmed and on the ground; after the control service restarted, a read-only ROS probe received two healthy FC EKF reports through the deployed decoder. Targeted CH6/EKF regression testing passed all 79 tests. The wider 179-test run still has two pre-existing failures in `test_moving_landing_stack.py` concerning the quality-gate body-frame expectation and moving-pad fusion error; those failures are outside this EKF decoder change. The next prop-less CH6 low-to-high test must verify that the executor sees the report and that the FC accepts GUIDED. A real flight transition remains unverified.

The published recovery set contains the normalized 1015-parameter snapshot and maintenance scripts, but excludes raw UART data, temporary backups and host-specific recovery files. The Pi-side TELEM1 maintenance script now uses ArduCopter 4.7 `MAV2_*` names, the same 10 Hz target, and a disarmed guard; it is deployed with the landing package but is not run by a service.

The Pi 4B USB-C port was configured in host mode, so it did not provide a USB network interface during this repair. Remote access therefore remained on the existing private LAN; no host address or network credential is stored here.
